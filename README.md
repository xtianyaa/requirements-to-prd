# requirements-to-prd

**把原始需求整理成可评审、可追溯的 PRD。**

一个供 Codex 使用的 AI Skill。支持从招标文件、需求书、功能清单和访谈记录出发，梳理产品范围、用户任务、业务流程和页面字段，保留原文依据，并指出仍需决定的问题。

当前版本：**v1.7** · [技能定义](SKILL.md) · [安装](#安装) · [快速开始](#快速开始) · [回归场景](evals/scenarios.md)

## 为什么做这个项目

原始材料往往同时包含功能描述、技术要求、实施约束和未解决的业务问题。直接扩写成一份长文档，容易遗漏要求，也容易把推测写成已经确定的规则。

requirements-to-prd 为 AI 提供一套需求整理与核验方法，让生成的文档能够回答：

- 这个产品服务谁，要完成哪些任务？
- 每项设计对应哪条原始要求？
- 业务如何流转，页面需要展示和填写什么？
- 哪些内容已有依据，哪些只是候选方案？
- 当前可以继续做什么，哪些分支还缺少决定或验证？

## 主要能力

| 能力 | 说明 |
|---|---|
| 需求追溯 | 保留材料版本、条款或段落引用，已有需求 ID 在修订中保持可追踪 |
| 业务梳理 | 按用户任务、业务对象、角色和操作结果组织设计，覆盖自动处理和非页面要求 |
| 候选方案 | 信息不全时给出有依据、带假设的候选路径，分别标明事实、建议和待确认项 |
| 页面字段细则 | v1.7 默认展开范围内页面的查询、列表、详情、表单和操作输入，以及类型、必填、默认值、权限和校验 |
| PRD 评审 | 通过具体输入和业务场景检查流程、字段、状态与权限，说明后续设计和开发的条件 |
| 局部修订 | 按反馈调整相关页面、动作和上下游关系，保留其他已确认内容 |

## 适用场景

- 将招标文件或需求书转成产品需求文档，并逐项核对覆盖情况。
- 把零散功能清单、访谈记录整理成可讨论的业务方案。
- 在进入原型和开发前，补充页面字段、操作条件和未决事项。
- 评审已有 PRD，检查遗漏、矛盾和需要研发自行猜测的内容。
- 对既有设计进行局部调整，检查变更影响。

输入材料需要由当前 AI 环境实际读取。DOCX、PDF 等文件的解析能力取决于宿主环境，本仓库本身不包含文件解析器。

## 安装

### 在 Codex 中安装

向 Codex 发送：

```text
请使用 skill-installer，从 https://github.com/xtianyaa/requirements-to-prd
安装 requirements-to-prd 到全局技能目录。
使用 v1.7 对应的提交：24514d47c352515d478e8b397569d07881e830f4。
如果已经安装，请备份旧版后更新。
```

指定提交可以固定技能版本，避免安装到其他分支上的旧版本。该提交的 [SKILL.md](https://github.com/xtianyaa/requirements-to-prd/blob/24514d47c352515d478e8b397569d07881e830f4/SKILL.md) 包含 v1.7 的功能定义。安装后在下一轮对话中调用。

### 手动安装

1. 下载或克隆本仓库，并切换到所需版本；安装 v1.7 可使用上面的提交。
2. 在 Codex 技能目录下创建 `requirements-to-prd` 文件夹。
3. 将 `SKILL.md`、`README.md`、`references/` 和 `evals/` 复制进去，无需复制 `.git/`。

默认全局目录为：

| 环境 | 目录 |
|---|---|
| Windows | `%USERPROFILE%\.codex\skills\requirements-to-prd` |
| macOS / Linux | `~/.codex/skills/requirements-to-prd` |

设置了 `CODEX_HOME` 时，使用其下的 `skills/requirements-to-prd`。更新前请备份已有目录。

## 快速开始

附上原始文件，或提供 AI 可访问的文件路径，然后说明期望的输出范围。以下提示词可直接使用。

### 从需求书生成 PRD

```text
使用 requirements-to-prd，将这份需求书整理成完整 PRD。
保留原文来源和需求 ID，包含业务流程、页面字段细则与验收场景。
原文没有确定的规则请标明，并给出有依据的候选方案。
输出独立的 Markdown 文件。
```

### 评审已有 PRD

```text
使用 requirements-to-prd，评审这份 PRD 是否可以进入功能设计和开发。
按优先级列出具体问题、文档位置、影响和最小补充内容。
区分设计遗漏、业务尚未决定和下一阶段的技术规格。
本轮只生成评审报告，不修改原 PRD。
```

### 局部修改

```text
使用 requirements-to-prd，将审批操作并入现有详情页，保留审批待办入口。
检查相关字段、权限、状态、入口和返回方式，并核对原需求是否仍然覆盖。
只修改受影响的内容。
```

只需要概要时，明确说明“本轮仅梳理范围与业务概要，不展开页面字段”。已有文档模板时，可同时提供模板并要求沿用。

## 会得到什么

默认交付独立的 Markdown 功能设计；明确要求 PRD 时组织为 PRD，也可沿用指定模板。内容通常包括：

- 产品目标、范围、材料依据和需求对应关系。
- 用户角色、业务对象、主要流程与关键操作。
- 页面内容、字段、校验、读写条件和失败反馈。
- 自动处理、指标、非功能与实施要求中适用的部分。
- 候选方案、待决定事项、场景推演和后续工作条件。

页面字段的表达示意如下，实际字段和规则依据项目材料生成：

| 页面 / 动作 | 字段 | 类型 | 条件与校验 |
|---|---|---|---|
| 事件详情 / 申请延期 | 延期原因 | 多行文本 | 申请时必填，保留原输入 |
| 事件详情 / 申请延期 | 拟延期至时间 | 日期时间 | 与原期限比较；申请不直接改变有效期限 |
| 事件详情 / 查看进度 | 当前状态 | 只读结果 | 由已定义的业务动作产生 |

具体章节和表格按项目复杂度组织，不要求每份材料套用同一套目录。字段表和场景推演仍需评审，示例不代表项目业务已确认。

## 能力边界

这个 Skill 提供需求分析和文档生成方法，输出质量仍取决于材料完整性、模型执行和人工评审。

- 缺少依据的法规阈值、评分公式、审批岗位或授权规则，会作为待决定内容保留。
- 页面字段细则不包含完整视觉原型、数据库物理结构或接口请求响应规格。
- 文档推演、原型验证和真实系统测试分别记录；需求覆盖或字段齐全不能直接证明可开发、已实现或验收通过。
- 外部数据、模型、解密设备等能力，需要真实授权、样本和验证证据。
