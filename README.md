# requirements-to-prd

版本 1.3。把招标文件、技术需求书、功能清单和访谈内容转为可评审的功能设计，支持反馈修订，为后续 PRD 提供已确认的依据。

## 使用方式

提供原始材料并说明本轮范围。例如：

> 使用 requirements-to-prd，将这份原始需求整理为可评审的功能设计。先识别需求、业务规则、系统行为和主要流程，再说明功能如何组织到页面。保留来源，提出关键问题；不要把未知业务规则当成事实。

局部迭代可以直接指出受影响的任务：

> 将审批操作并入已有详情页，保留独立的审批待办入口。检查角色权限、返回方式、数据读取和原需求覆盖是否仍然成立。

## 处理与交付

需求依据和类型 → 用户任务、对象、规则与流程 → 页面组合 → 操作与数据 → 覆盖检查 → 用户评审与局部修订。

默认输出一份独立的 Markdown 功能设计，包含可追溯的需求、业务与页面设计、适用的非页面要求、覆盖映射和未决问题。文档可按规模精简，用户指定的模板优先。测试 Skill 时同样交付约定范围的设计成品，验证记录另附。

本版本重点是设计确认阶段。正式 PRD 可在用户要求时基于已确认结果继续编写；数据库、API 和架构设计不默认进入范围。文档中的“已描述”不代表用户已确认、软件已实现或验收通过。

## 文件

- [SKILL.md](SKILL.md)：入口、需求依据、业务梳理、覆盖和迭代规则。
- [页面组合规则](references/page-composition-rules.md)：任务如何落到页面、视图和容器，何时合并或拆分。
- [页面数据与操作规则](references/page-data-flow.md)：读取、提交、系统行为、结果反馈与跨页面关系。

## v1.3 的主要调整

根据实际 PRD 评审补充以下要求：

- 多角色、多状态任务展开“当前状态、适用分支、具体角色、动作与下一状态”，并交叉检查流程和页面条件。
- 页面组合比较任务、对象、周期、查询、明细和操作；多视图页面明确默认视图、导航、筛选继承及内容关系。
- 页面关系先解释对象关联与结果数量，再决定直接跳详情还是经过关联列表选择。
- 待确认项按可独立回答的决策拆分，记录影响、阻塞范围及确认状态。
- 用具体输入、动作和预期结果推演场景，区分纸面检查与实际运行验证。
- 产品正文集中说明业务和操作，材料处理与测试过程放在说明或附录。

本次发布包含此前本地 v1.2 的改进：

按需求类型选择设计落点，自动处理和非功能要求不必对应页面；业务流程在页面设计前梳理；页面组织、呈现容器和交互方式分别描述；角色差异不自动导致拆页；展示结果与系统行为分别检查覆盖。

保留待确认项和设计建议，按实际描述程度记录覆盖状态。主文件通过链接加载详细规则，减少重复。版本信息放入 metadata，兼容 Codex Skill 的基础格式校验。
