# requirements-to-prd v1.1

将招标文件、技术需求书、功能清单、业务需求说明等原始材料，转换为**可评审的第一版功能设计**。

核心目标：

> 先把原始需求变成“看得见的系统”：功能如何组合成页面、页面展示什么、用户怎么操作、数据如何流动、业务流程如何走通。

它不是最终 PRD 生成器。

## v1.1 相比 v1.0 的主要增强

### 1. 增加“功能如何组合成页面”的明确规则

不再采用“一功能一页面”。

先识别：
- 用户任务
- 核心业务对象
- 数据上下文
- 角色/权限
- 生命周期
- 信息复杂度

再决定页面边界。

### 2. 增加页面组合候选表

在正式页面设计前，先说明：
> 哪些功能为什么组合到同一个页面。

便于人工评审页面颗粒度。

### 3. 增加页面颗粒度复核

重点检查：
- 页面是否过细；
- 是否可以合并；
- 是否存在重复页面；
- 是否把按钮/指标/流程节点机械拆成页面。

### 4. 每个页面强制输出页面数据流

页面必须说明：

> 数据输入 → 数据来源 → 页面处理 → 页面展示 → 用户操作 → 数据回写 → 下游去向

数据来源不明确时必须标记“待确认”。

### 5. 页面修改必须同步检查数据流

页面合并、拆分或操作调整后，需要重新检查：
- 页面数据流；
- 页面之间的数据传递；
- 业务流程；
- 需求覆盖。

## 推荐工作方式

1. 输入原始需求
2. 提取需求
3. 识别用户任务
4. 建立功能树
5. 建立功能组合候选表
6. 设计页面
7. 输出页面数据流
8. 梳理业务流程
9. 做需求覆盖和一致性检查
10. 用户评审
11. 根据反馈局部修改
12. 用户确认
13. 再进入正式 PRD
