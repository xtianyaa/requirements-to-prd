# 企业联系人 PRD（可评审稿）

> 本文档为合成需求「企业联系人」的产品需求说明，材料完全虚构，用于公开评测，不包含任何客户资料。
> 文档约定：凡标注【事实】的条目来自原始需求原文；凡标注【设计建议】的条目为作者提出的待评审假设，需业务方确认后方可定稿。数据库与 API 不在本 PRD 范围内。

---

## 1. 背景与目标

### 1.1 背景
企业内部存在多类"责任人"角色，需要在通知触达、工单分派、合规与应急处置等场景中快速定位到正确的联系人。当前缺乏统一的联系人维护与生效规则，导致通知发错人、工单无人认领、人员离职后仍被分派等问题。

### 1.2 目标
- 【事实】维护五类责任人档案：合规联络人、数据安全负责人、经办人、技术联系人、应急联系人（对应 C01）。
- 【事实】支持联系方式校验、有效期、离职或变更登记，并用于通知与工单匹配责任人（对应 C02）。
- 【设计建议】提供联系人列表、查询、详情与维护动作，形成可评审的字段候选集，作为后续细化评审的输入。

## 3. 角色定义（对应 C01）

| 角色 | 职责定位（建议） | 通知场景（建议） |
|------|------------------|------------------|
| 合规联络人 | 对外对接监管/合规事务 | 合规检查、监管函件 |
| 数据安全负责人 | 数据安全事件第一责任人 | 安全事件、漏洞通报 |
| 经办人 | 具体事项/工单的执行人 | 工单分派、流程催办 |
| 技术联系人 | 技术接口/系统对接人 | 系统变更、技术告警 |
| 应急联系人 | 突发事件紧急联络 | 应急响应、7×24 告警 |

> 以上"职责定位"与"通知场景"为【设计建议】，原文仅给出角色名称，未定义职责边界。

## 4. 功能范围

本 PRD 覆盖四个视图/动作：

1. **列表**：按角色/状态/有效期浏览联系人。
2. **查询**：按关键字段检索与筛选。
3. **详情**：查看单个联系人完整信息与履历。
4. **维护动作**：新增、编辑、变更登记、离职登记、停用/启用、联系方式校验。

【设计建议】不覆盖：组织架构管理、单点登录、消息发送通道本身（短信/邮件网关）——这些仅在"通知"与"校验"时作为外部依赖被调用。

## 6. 属性定级：设计建议 vs 事实缺失

本节将 C03 的每一项拆解，明确"可先按建议推进"与"必须等业务拍板"两类。

### 6.1 联系方式字段（缺失 → 建议候选）
- 【缺失】原文未指定联系方式包含哪些字段。
- 【设计建议】候选字段：手机号、固定电话、邮箱、企业 IM 账号、备用手机号。默认以「手机号 + 邮箱」为最小集合，二者至少填一项。
- 校验规则建议：手机号按 11 位格式 + 归属校验，邮箱按 RFC 格式 + 域名校验；校验失败则标记"校验失败"并阻断通知。

### 6.2 必填组合（缺失 → 建议候选）
- 【缺失】未规定每个角色的必填字段组合。
- 【设计建议】分角色差异化：
  - 应急联系人：手机号必填（需 7×24 可触达），邮箱可选。
  - 数据安全负责人：手机号 + 邮箱均必填。
  - 经办人/技术联系人/合规联络人：手机号与邮箱至少一项。
- 此项建议需业务确认，尤其应急联系人是否要求双联系方式。

### 6.3 一人可否多个角色（缺失 → 建议候选）
- 【缺失】未说明一人能否兼任多角色。
- 【设计建议】允许一人兼任多角色（如技术联系人兼任经办人），角色字段支持多选。若业务要求互斥（如合规联络人与数据安全负责人不得同一人），作为可配置约束。

### 6.4 每个角色人数（缺失 → 建议候选）
- 【缺失】未规定每角色人数上限/下限。
- 【设计建议】默认每角色至少 1 人、不设硬上限；应急联系人建议至少 2 人形成主备。是否需要"唯一主责任人"由业务确认。

### 6.5 有效期空值/边界（缺失 → 建议候选）
- 【缺失】未说明有效期可否为空，及起止边界规则。
- 【设计建议】默认规则：
  - 有效期开始日期必填（默认登记当日）。
  - 截止日期允许为空，表示"长期有效"。
  - 截止日期必须晚于或等于开始日期。
  - 到期当天 24:00 后视为"已过期"，过期联系人不出现在通知与工单匹配候选。
- 需确认：是否允许"长期有效"（空截止日）这一语义。

### 6.6 审核路径（缺失 → 建议候选）
- 【缺失】未说明联系人新增/变更是否需要审核。
- 【设计建议】默认「登记即生效，留痕可追溯」；如需审核，可选"部门负责人审核后生效"的开关。是否引入审核由业务确认。

### 6.7 匹配优先级（缺失 → 建议候选）
- 【缺失】未说明一人多角色或多候选时，工单/通知如何选人。
- 【设计建议】候选排序建议：
  1. 角色匹配度（完全匹配 > 多角色命中）；
  2. 有效期状态（生效中优先）；
  3. 是否主责任人（如有）；
  4. 最近变更时间（新登记优先）。
- 应急通知建议走"主备轮询"（先主后备）。此排序为待评审假设。

### 6.8 离职后在途工单处理规则（缺失 → 建议候选）
- 【缺失】未说明离职登记后，其名下在途工单如何处理。
- 【设计建议】三种候选策略，需业务二选一或组合：
  - **自动转派**：按同角色在岗人员自动改派；
  - **指定接管**：离职登记时必填接管人；
  - **挂起待处理**：标记"待人工改派"进入待办队列。
- 建议默认"自动转派 + 允许指定接管"。

## 7. 具体场景

### 场景 1：新增应急联系人并校验联系方式
1. 管理员录入张三为"应急联系人"，手机号 138****1234、邮箱 zhangsan@example.com。
2. 系统触发联系方式校验：手机号格式通过、邮箱格式通过。
3. 校验通过，登记生效，有效期默认当日生效、截止为空（长期有效）。
4. 张三进入应急联系人列表，状态"生效中"。
- 【关联缺失】若邮箱校验失败，是否阻断保存？建议"阻断保存并提示"（见 6.1）。

### 场景 2：变更登记
1. 李四由"经办人"变更为"技术联系人"，原经办角色注销。
2. 系统登记变更履历：变更前角色=经办人，变更后角色=技术联系人，登记时间、登记人。
3. 变更立即生效，旧角色下的在途工单按匹配优先级重新匹配责任人。
- 【关联缺失】角色变更是否需要审核？默认不审核（见 6.6）。

### 场景 3：离职登记与在途工单
1. 王五（经办人）办理离职，登记离职日期。
2. 系统识别王五名下 3 个在途工单，按"自动转派"策略改派给同角色在岗的赵六。
3. 王五状态置为"已离职"，从通知与工单匹配候选中移除。
- 【关联缺失】若采用"指定接管"，则离职登记时必填接管人；本场景按默认"自动转派"执行（见 6.8）。

### 场景 4：通知触达与过期过滤
1. 系统需向"数据安全负责人"发送安全事件通知。
2. 匹配候选人：角色=数据安全负责人、状态=生效中、有效期未过期。
3. 若唯一候选人的手机号校验失败，则通知失败并告警，需人工介入。
- 【关联缺失】过期当天是否仍视为有效？建议按 6.5"到期当天 24:00 后过期"处理。

## 8. 下一步可以做什么

1. **澄清 C03 各项**：以第 6 节为清单，向业务逐项确认（建议用选择题形式收敛：联系方式集合、必填组合、多角色、人数、空值语义、审核、优先级、离职策略）。
2. **确认角色职责边界**：第 3 节的职责定位为建议，需业务确认"合规联络人"与"数据安全负责人"是否可兼任等。
3. **评审字段候选**：在 5.1–5.4 基础上删减/补充字段，形成定稿字段字典（字段名、类型、必填、枚举值、校验规则）。
4. **定稿匹配优先级与离职策略**：将 6.7、6.8 的建议落地为规则表，作为后续实现与验收依据。
5. **补充验收标准**：为列表、查询、详情、维护动作四个视图编写验收用例（如"离职登记后 1 分钟内不再出现在匹配候选"）。
6. **确认非功能要求**：通知时效、联系方式校验频率、变更留痕保留周期等。
