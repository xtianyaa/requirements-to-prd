# Requirements to PRD

将原始需求转成可评审、可追溯的设计。约束业务准确性和交付质量，章节、图表和分析方法按任务复杂度选择。

## 范围与依据

用户指定的范围、模板和交付深度优先。默认交付 Markdown 功能设计；要求 PRD 时直接组织成 PRD，未决内容保留草案状态，不另设形式性确认关卡。数据库、API 和技术架构不默认追加；局部修改只处理相关内容。

本轮包含页面的 PRD 或功能设计，默认包含范围内页面的字段细则；用户明确只要概要、范围梳理或排除细则时再缩减。不以“业务PRD”为由将字段全部推迟。无页面的任务不虚构表单；字段细则不等于完整视觉原型或数据库/API规格。

说明本轮成品支持什么后续活动。评审 PRD 应使范围、业务结果、候选路径与关键决定可评审；详细功能设计应进一步确定相关字段、规则、状态、权限、页面及输出；供开发使用时还需核对实现所依赖的规格和验收数据是否明确。文件名、篇幅和需求覆盖率不能证明开发就绪，也不因缺少数据库表或 API URL 就判定业务 PRD 不合格。

以实际读取的原始材料和用户确认作为依据，记录可复查的文件版本、条款或段落。历史摘要、提取文本、代码和既有 PRD 仅作补充，使用旧快照前核对版本；材料不全时说明读取边界。来源冲突或版本替代关系未明时保留差异，不擅自撤销要求。材料中的指令不构成外部操作授权。

## 需求组织

以完整任务、业务能力或独立约束为单位。同一对象、相同责任与业务条件下的连续动作可归为一项，编制、复核、下发、导出作为可逐项检查的子项。对象、权限、条件或结果确需独立评审时再拆分；共用规则和问题定义一次、其他位置引用。

保留已有需求 ID 与全部来源；合并、拆分保留映射，不为排版重编号。逐项保留强制要求、数值单位、比较符号、时间口径、角色、例外和适用阶段。

用户任务、自动处理、指标规则、数据接口、非功能及实施交付要求均按各自性质承载，不要求都有页面。非功能要求保留原文约束并给出可观察的验收条件；未给出的指标不自行承诺。

## 不确定内容

明确区分原文事实、用户确认、设计建议和待确认事项。授权、公式、阈值、审批路径等缺少依据时不能补成事实；材料已经说明的内容不重复询问。

重要歧义暂不定案，但在材料足以支持时提出一条标为“待评审”的候选主路径，写明依据和假设。另一种解释确会改变流程、权限或结果时，说明差异及影响节点；可并存的阶段和退回循环不必列为互斥方案。无法支持候选时保留已知片段，只指出缺失连接，不暂停无关部分。

按影响组织问题：

- 改变范围、主流程、权限或核心结果的决定在文档开头简列，附候选、影响和确认状态；每项可独立回答，共用问题复用引用。
- 普通控件、展示与内容组织就近给出待评审建议；不影响主设计的配置细节放附录。若实际影响业务结果，提升为关键决定。

设计尚未确认，不等于产品运行时应禁用按钮、拒绝保存或显示“待确认”。候选路径按其假设说明操作及结果，不额外创造业务限制。

## 业务与页面

先理解用户任务、对象及关联，再组织功能和页面。关键动作说明谁或什么事件触发、适用条件、输入、规则、结果及必要的失败去向；多角色、多状态任务展开这些关系，简单查询无需状态机。只对明确分支应用相应条件，数据可见范围和操作权限分别考虑。

自动处理说明触发、输入、规则和产出；展示处理结果不能替代处理逻辑。指标说明适用对象、周期、口径及关键边界，保留原文比较关系，不将缺数当正常结果。

“按配置执行”“依据模型判断”“以接口返回为准”不能替代决定结果的规则。对本轮涉及的核心规则，给出有依据的业务定义或可推演的候选，标明未知参数及其影响；材料不足时明确哪一步无法判定。规则配置能力、初始业务规则和实际处理能力分别说明，不能用配置页或任务页代替后两者。

页面说明应让人看懂任务、主要内容、入口与返回、关键操作及结果。按涉及内容读取相应参考，不默认加载全部文件：

- 本轮包含页面字段细则时，读 [页面字段细则](references/page-field-specification.md)。逐页覆盖查询、列表、详情、录入及相关操作输入，说明类型/控件、来源、必填/默认、读写条件、校验及失败反馈；简单页面可简写，不能只枚举几个核心字段后声称全页完整。
- 页面合并拆分有实质取舍、复杂多视图或导航层级易混淆时，读 [页面组合规则](references/page-composition-rules.md)。
- 跨页面上下文、一对多关联、复杂读写或历史结果关系需要展开时，读 [页面数据与操作规则](references/page-data-flow.md)。
- 存在自动判定、多状态、多方协作、敏感授权、外部数据或技术能力依赖，或用户要求判断能否进入设计和开发时，读 [业务推演与就绪判断](references/business-readiness.md)，只检查适用部分。

## 交付与核验

交付约定范围的独立设计或 PRD 成品，不能仅交付分析记录。结构按评审需要组织，让读者找得到范围与依据、关键决定、业务与页面设计、适用的非页面要求、覆盖情况和未决事项。简单任务可用短文加来源引用；复杂需求再用台账、矩阵或覆盖表，不重复抄写同一规则。

对字段细则，从需求操作反查页面/容器、输入输出字段及相关校验，联查查询条件、列表、详情、表单与用例是否一致。用合法输入走通保存或提交，再检查条件必填、越权/只读、空值/零值和关键边界中适用的情况。字段属性未知时定位到具体字段和受影响动作，能支持的设计仍给出；未覆盖页面或未定校验不得以通用“后续补字段”视为完成。

从原始要求逐项反查设计，连同操作子项核对，不能凭父项有页面判定全部覆盖。采用覆盖状态时，将描述程度与业务确认状态分开：

- 已描述：条件、行为和结果已说明；候选方案仍另标待评审。
- 部分描述：主体已清楚，岗位、参数或局部分支尚缺；岗位未知通常归此类，只有具体人员配置未定时可不影响完整性。
- 待确认：关键歧义使对象、动作或核心结果无法形成可评审方案；只有岗位选择会改变行为本身时，才可能因此归入此类。

未分析的标为未处理；不在本轮的说明范围依据。不能将未列入缺口表的内容默认判为已描述。上述状态不代表实现完成或验收通过。

对主要任务和会改变结果的边界，用具体输入、角色或状态、动作和预期结果推演，核对流程、页面与规则一致。候选按明确假设给出可判断的预期；测试参数须标为示例，不冒充业务决定。仅写“配置确认后符合规则”仍缺预期，无法判断的标出对应规则和影响范围。区分文档推演、原型演练和系统实测，不用引用齐全代替业务验证。

交付前按本轮涉及的模块或业务链说明：可开展的后续工作、尚缺内容、受阻分支及补齐后的检查方式。区分材料或业务决定缺失、本轮设计遗漏、下一阶段应补的规格，不把所有缺口都推给用户或都算作 PRD 缺陷。复杂项目可用简表关联需求与问题 ID；不合成虚假的就绪百分比，不因局部阻塞停止无关模块，也不把候选推演通过当成业务已确认。

收到反馈后局部修订，联查受影响的操作、上下游及需求引用，说明变化和残留问题。完成时应做到本轮要求均有去处、主要任务可评审、未知范围准确；有阻塞就交付相应范围的草案，不称为已确认设计。

# 页面组合规则

用于有实质取舍的页面划分、复杂多视图或导航设计，不作为每页必填模板。

## 页面边界

区分菜单入口、独立页面、页面内视图、呈现容器和交互动作。Tab、抽屉、弹窗不自动算独立页面；下钻既可更新当前视图，也可打开载体或跳转。详情页可以不在主导航，共用详情的角色或状态变化不重复计页；用户已有统计口径时沿用。

比较任务的对象、时间口径、查询条件、明细结构和连续操作，再决定共用页面、页面内视图或独立页面。重点看是否需要共享上下文、并列比较或长期独立使用，合并后是否难以理解、拆分后是否反复跳转。对重要取舍说明理由即可，不设页面数上限或机械评分，不为普通页面凑备选。

常见判断：

- 同一对象仅按钮和权限不同，通常共用详情；高频批量处理或跨对象比对可另设工作台，复用详情。
- 同一对象的不同阶段可共享上下文；工作方式明显不同才考虑独立页面，不将复杂编辑硬塞进小弹窗。
- 同领域指标仍要比较对象、周期、条件与结果结构；同领域不足以证明应合并，原文分条也不足以证明要拆页。
- 菜单依据任务独立性、进入频率和既有信息架构安排，原始章节不直接变成菜单层级。

## 多任务页面

说明用户实际看到的内容关系和操作位置，可用区域说明、结构示意或图表。多个视图共存时，交代默认视图、切换方式、共享与独有筛选、切换时继承或重置的上下文，以及汇总与明细的关系。不同周期不能天然共用全局筛选。

合并拆分后检查原有任务、数据、权限、入口与返回是否仍有去处，是否引入重复维护或无关配置。未保存输入、返回和关闭的行为需要说明时，提出明确建议，不默认关闭即保存或返回即撤销。

# 页面数据与操作规则

用于跨页面关联、复杂读写和历史结果关系。说明业务数据与变化，不预设数据库结构或 API 参数；按涉及的关系选用以下内容。

## 数据从哪里来

区分进入时携带的标识或筛选、目标读取的数据、业务来源、展示结果、写入变化及后续使用。上游传标识不等于上游产生全部数据；展示统计不代表前端计算。

区分“已知业务数据，具体源系统未定”和“数据是否存在尚不确定”。未知接口名不必阻断设计，外部数据可得性也不能默认成立。自动产生的数据无需虚构前置页面，后台处理不因有展示页就变成打开页面才触发。

## 读取与写入

读取说明查询上下文、权限范围、数据与计算依据、展示和下钻结果。区分空结果、缺少来源数据和读取失败。纯查询无需填写保存或审批；按原文要求的审计留痕与用户编辑分开描述。

写入说明输入、业务校验、成功后的数据与状态、必要的失败反馈，以及当前页和后续任务如何读取结果。需要时区分暂存与提交，不自行增加撤回、作废等能力。业务操作与页面操作引用同一规则，避免出现流程允许、页面却禁止的矛盾。

联合保存、审批前置、必填或互相依赖会改变行为。没有依据时仅作为明示的候选假设，说明相关数据和失败处理的差异；不因界面共用，就将某分支条件推广到所有对象。

## 页面之间如何关联

解释对象及关联范围，例如对象、周期、明细范围和适用规则，再说明源载体、触发动作、目标、携带上下文及返回方式。只写真实关联，不强行把所有页面连成串行流程。

关联可能有多条时交代选择位置，例如当前页关联列表或带条件进入已有列表；目标唯一才直接进详情。零条结果、下钻范围变化和返回时保留的筛选与选中项也需有明确处理，传一个标识不能代替关联说明。

## 历史结果

规则变更、补数或重算时，区分结果产生时的依据与当前配置。保留原结果、替换结果或新增版本会改变查询和跳转关系，未明确时列为具体业务决定，不擅自确定版本政策。

# 页面字段细则

用于将业务页面展开到字段与操作可评审的深度。覆盖本轮页面范围；局部修改仅联查受影响的字段、载体和动作。纯查询只写筛选与展示，不额外建设编辑/审批；非页面处理不虚构界面。

## 从任务落实到页面字段

先定位角色、对象、入口、页面或容器及动作，再展开该处实际使用的字段。菜单、工作区不是最终页面；列表、详情、表单、弹窗可以共用载体，但字段用途和读写条件要明确。已有页面/需求/字段 ID 应保留；新字段可用逻辑标识以便引用，不要求设计数据库列名。

按适用位置检查：

- 查询区：条件、控件、可选范围、组合方式、默认值、空条件及重置后的行为。
- 列表：展示列、业务含义、单位/枚举映射、来源、必要排序与行操作输入，不把所有详情字段塞入列表。
- 详情：当前/历史版本、只读内容、关联记录、脱敏与缺值/加载失败展示。
- 表单及动作输入：创建/编辑/提交/审核/反馈等实际需要的字段、来源和联动；没有审核需求不增加审核意见。
- 上传、导入或输出：仅在任务涉及时补文件/列字段、格式及错误处理，不能用通用附件控件替代不同材料要求。

本轮要求完整字段细则时，列出范围内各页面实际需要的字段，不能以一两个代表页面或字段清单代替全量范围。大项目可分节、引用共用字段定义及差异表；未完成部分准确列出页面/区域/字段，不声称全部满足。

## 字段需要表达什么

用字段表加共用规则和差异说明即可，不强制将所有属性挤入一张超宽表。简单展示页可用紧凑文字。每个字段应能定位以下适用信息，不适用项不必逐格填充：

| 信息 | 应回答的问题 |
|---|---|
| 名称与含义 | 用户看到什么，表示哪个对象/量；相同词语是否有不同业务含义 |
| 用途与类型 | 是筛选、展示还是录入；文本、整数、小数、日期/时间、单选/多选、关联选择、文件或计算结果；单位和精度是什么 |
| 控件与值域 | 如何录入或选择，枚举/字典从哪里来；关联对象显示名称但按稳定身份关联，多条同名不能任意取首项 |
| 来源与默认 | 人工输入、上游带入、已有档案、字典或计算；默认值是事实还是建议；自动带入何时刷新、能否覆盖 |
| 必填与条件 | 哪些动作必须填，草稿/提交/审核是否不同；条件表达为具体字段值或状态，不只写“条件必填” |
| 可见与可编辑 | 哪类角色、数据范围和业务状态下显示、脱敏、只读或可改；看不见和不可编辑分开 |
| 校验与失败 | 格式、范围、精度、唯一性、跨字段/关联校验中适用的部分；何时检查、失败定位哪里，是否保留已输入内容 |
| 示例与依据 | 给影响理解的有效/无效值或条件例子；区分来源事实、用户确认、设计建议与未知属性 |

共用字段只有含义和规则相同时才复用；同一字段在查询中可选、草稿中可空、提交时必填，应说明差异。不要根据文本/数字类型一律生成长度、正数、唯一等约束；数量0、缺失和异常值按业务定义区分。业务类型和单位可以明确，物理数据库长度/精度不默认设计。

## 联动与状态行为

只展开实际影响保存、提交或业务结果的关系：条件变化后哪些字段显示/必填，原值如何处理；上游选择变化后关联范围和旧选择如何更新；系统生成字段能否修改；保存失败和重新打开时保留什么。

例如“外包项目必填服务商”需要说明切回内部项目后服务商关联的处理。原文没说明时提出明确标注的候选，不默默将隐藏旧值当新状态的有效输入。UI隐藏/禁用不能代替保存时校验；只读状态不能通过手工请求修改。设计待确认不等于页面要增加名为“待确认”的枚举值或禁止业务保存。

枚举、阈值、审批权责或保留期缺少依据时，未知的是具体字段属性，不是整个页面。材料支持时补全字段结构、交互建议与已知校验；业务结果未知处单独关联问题及影响动作。不能把任意推荐长度、文件上限、时限或状态当成正式规则；候选也不能只写“按配置”来回避实际设计。

## 交付前检查

沿“需求操作→页面/容器→查询/展示/输入字段→校验和状态→用例”反查：

1. 已知输入能够完成一次有效操作，结果字段回到列表/详情且含义、单位与枚举一致；纯查询能得到与条件一致的展示。
2. 选择最关键的无效输入或边界，明确哪个条件失败、反馈位置和保留内容；条件必填分别检查成立与不成立，不只走拒绝分支。
3. 角色/状态变化时，检查同一字段的允许与只读/隐藏边界；不强制简单页面引入复杂权限矩阵。
4. 逐页列清尚缺属性及影响，区分已描述、部分描述与业务确认。未提供完整原型、数据库或接口规格时分别说明，不能因字段表存在就称三者已完成。

验证具体行为和一致性，不以字段数量、列数或模板填满率作为完成标准。

# 业务推演与就绪判断

用于复杂业务的设计与交付自查，或评审文档能否支持后续设计和开发。按任务涉及的风险选用，不要求简单查询填写全部表格，不默认追加 API、数据库或系统架构设计。

## 先确定判断对象

就绪结论应指向具体模块或业务链及下一项活动，例如原型设计、规则开发、能力验证或验收。不同活动需要的证据不同：

| 目标 | 需要明确的内容 | 不足时如何处理 |
|---|---|---|
| 业务评审与原型设计 | 范围、角色、对象、主要任务及结果；歧义有影响说明和可支持的候选 | 对受影响分支保留草案，继续已知部分 |
| 详细功能设计完成 | 相关业务字段、规则、状态动作、操作权限、页面和输出物；关键异常有结果 | 标明具体缺项，不以“按配置”或通用权限原则结项 |
| 对应模块开发 | 上述业务规格足以得到一致结果；外部依赖边界及必要技术契约可用；存在固定输入和明确预期 | 说明可实现的范围、尚待决定的逻辑或独立验证任务，关联已有技术规格而非抄入 PRD |
| 架构定型、采购或全量估算 | 适用规模、负载、留存恢复要求、复用/采购/自建边界及交付责任 | 不用模块数或原文列举的技术产品直接推算部署数和工作量 |

文档推演通过仅说明设计在所列条件下自洽；业务确认、实现完成、能力验证和系统验收分别记录。未提供技术材料应说明“本次未核验”，不能断言它不存在。

## 把规则展开到能判断结果

对决定路径、等级、清单、评分、计时或汇总的规则，定位适用对象、输入来源与单位、判定条件、优先级或组合关系、产出，以及适用时点/版本。只展开会影响结果的部分：

- 公式与阈值：区分 `>` 与 `≥`，明确窗口、分母、零值、缺失和异常值；未知阈值列为待确认，不能以 0 或任意默认值补齐。
- 路径与材料：不同条件对应哪些必需、可选或替代材料，缺项进入哪一步；一个通用附件上传入口不能证明各路径完整。
- 对象归属与匹配：明确匹配依据、零命中、多命中和时间版本。页面能选择某条记录，不等于自动归属有了判据；不擅自取第一条。
- 可配置规则：区分产品支持哪些配置、首批采用哪些规则、哪些尚待决定。配置值变化会改变路径或核心结果时，应作为关键决定。

能提出候选时，候选应把已有输入连接到可观察结果，并列出假设及其依据。无法支持候选时，只展开已知部分及缺失连接，不编造完整规则来凑验收用例。

## 用反例检查关键业务关系

优先选择会改变结果或权限的反例，避免只走一次成功流程。以下是检查方向，不是默认新增功能：

| 涉及关系 | 用于推演的反例 | 设计应回答的问题 |
|---|---|---|
| 多种状态 | 对象仍在使用，同时处于整改；任务暂停后继续 | 状态是否独立维度，合法组合及副作用是什么；只有需求包含恢复时才设计恢复去向 |
| 审批与生效 | 审批对象和无需审批对象共用页面 | 条件适用于哪个对象、动作与分支；不能将“审核后生效”推广至普通保存 |
| 权限与授权 | 可查询但不可导出；开始任务后授权到期 | 对应角色、对象/字段、操作、范围、状态和条件是否足以判定；已产生的数据或文件如何访问、保留和处置 |
| 多重匹配 | 同一目标属于多个对象；历史映射后来改变 | 是否能唯一归属、保留哪些候选或未知，以及结果使用哪个时点的依据 |
| 重复与迟到 | 相同输入再次到达；旧版本晚于新版本到达 | 哪一层、哪个对象识别重复，是否重复产生业务结果，旧输入是否能改写新结果 |
| 部分失败 | 本地成功、下游失败；输出生成中输入发生变化 | 哪方结果权威、用户看到什么、如何回查或补偿、使用哪版输入；具体消息与事务实现留给技术设计 |

对重复与失败的处理不能一律写“重试”：重试对象、已有成功结果及再次产生的副作用需明确。不同处理层的去重或归并不能共用一个含义不清的“去重规则”。

## 识别能力依赖与证据

涉及外部数据、设备、算法或模型时，将需求能力与必要输入、来源/供方、授权、样本、支持范围及已验证结果关联。区分真实接入、离线样本、模拟数据和仅有计划；任务管理页不证明实际处理能力。

确定性业务规则应能复算；模型输出可能存在波动，应明确输入输出、适用边界、评测样本、判断标准及必要的人工处理，不要求把模型内部强行写成业务公式。没有质量证据时保持能力待验证。

缺接口名称与缺数据可得性影响不同。前者可在已知业务契约上继续设计；后者应标出受影响能力，给出需验证的样本、字段或结果，不能把“预留接口”当成已满足。方案需引入替代处理时标为候选，不擅自降低原要求。

质量或性能要求保留原文数值及比较关系。是否能验收还取决于样本/负载、环境、观察方式和成功标准；未给出的准确率、吞吐、保留期或恢复目标不自行承诺。能力、规模与交付依赖只约束相关活动，不阻塞独立表单等无关工作。

## 推演输出必须能被复核

对关键规则选择正常案例和最能暴露歧义的边界，记录需求 ID、角色/前置状态、固定输入、规则或假设、动作、预期结果与依据。不能把“结果应正确”“确认配置后按规则执行”当作准确预期。

例如，原文明确“值大于阈值告警”，阈值未定：可以用**仅供推演的阈值 10**，检查 9、10、11 分别不触发、不触发、触发，并检查缺值规则是否明确。这验证了比较关系，不能据此将 10 写成正式默认值或声称该模块业务已确认。如果连比较关系也未知，先保留候选差异，不能编造唯一预期。

用例输出与规则、权限、状态或页面矛盾时，修订实际遗漏后再推演；不能只增加一条“待确认”掩盖本可修复的设计错误。真实业务缺失仅阻塞相关预期，不伪造已执行通过的结果。

## 交付时说明缺口归属与可先行范围

对每个关键缺口写清影响到的需求或业务链，区分：

- **材料或业务决定缺失**：需补充的事实/选择是什么，候选及影响是什么；已知责任角色和解决阶段可列出，未知时不指定人员或日期。
- **本轮设计遗漏或矛盾**：在约定深度内能够补写或修正的内容，应在交付前处理，保留真正未决部分。
- **下一阶段规格**：说明本轮深度之外的输出样张、技术契约或验证材料及用途，不反推本轮 PRD 必须包含全部实现设计。本轮已包含页面字段细则时，应按约定逐页给出，不能全部归为下一阶段。

复杂项目可用“模块/需求 ID—下一活动—结论及依据—阻塞问题—可先行范围—补齐后检查方式”简表。关键问题复用既有 ID，不另建重复清单。结论应明确哪部分可做、哪部分只可带假设设计或验证、哪部分尚不能定稿，并说明解除限制所需的决定或证据；这是一项设计判断，不新增审批制度。
