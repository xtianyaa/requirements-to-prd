# requirements-to-prd 回归场景

供维护 skill 时使用，不是每份 PRD 的固定检查表。每个案例使用独立上下文，提供当前 skill 和下列请求；检查实际产出中的行为和结论，不以标题、关键词或表格数量计分。记录使用版本、输出、符合项和残留问题；人工自查、独立模型评测和系统实测应分别标明。

## A：简单需求不被过度设计

请求：将以下需求整理为简短的评审 PRD：“访客可查看已发布公告，按标题关键词查询，打开详情查看标题、正文和发布日期。”只做本轮功能设计，不涉及后台维护。

检查：能直接说明查询与详情的行为、空结果和返回；不扩建发布审批、状态机、数据库/API 或大套矩阵；能说明可继续页面设计，不能声称系统已实现。常规交互建议标明建议，不伪装原文。

## B：部分条件不能泛化，状态可以共存

请求：整理企业管理详细功能设计。企业可同时处于已入驻和整改中；管理员可暂停/恢复其数据接入。联系人修改保存即生效，资质变更需复核通过后生效。原文未给出复核岗位，也未说明暂停是否影响整改期限。

检查：区分入驻、整改、接入状态及操作影响；不让联系人修改套用审批条件；提出有依据的复核岗位候选或保留权责缺口；暂停对期限的影响明确待决定，不擅自暂停所有业务。已知流程可继续设计，受影响分支及补齐方式明确。

## C：未知阈值与可执行推演

请求：整理预警 PRD。每小时统计对象的累计量，大于阈值时告警。阈值由业务确定，目前暂缺；零值是有效值，未收到数据应标记缺数。需要配置阈值的功能。

检查：保留小时窗口、严格大于、零值与缺数的差异；区分配置能力与初始阈值；可以使用明确标注的示例值推演等于及两侧边界，不能把示例当正式阈值。不能以“参数未确认”新增运行时禁用或审批发布限制，也不能称规则已可正式验收。

## D：多重匹配、重复与部分失败

请求：设计自动事件归属和建单。事件依据出口地址和目标域名匹配企业及业务场景；多个企业可能共享出口，一个企业多个场景也可能使用同一域名。采集会重复投递，事件创建后推送到工单系统，推送可能失败；归属映射会随时间改变。原文未给出唯一标识、匹配优先级或合并窗口。

检查：不取第一个匹配项、不把出口地址当企业唯一标识；识别历史时点、重复识别与事件/工单责任边界的缺口；给出可支持的候选及已成功事件如何回查/补偿的问题，不只写重试。指出哪些决定影响自动归属与建单，不编造接口 URL 或唯一键作为事实。

## E：授权与真实能力证据

请求：整理审查模块 PRD。企业可授权审查员在有限时段查看样本并运行内容识别，只有企业管理员能导出结果。外部供方计划提供数据，尚无样本和接口承诺；演示页已有模拟结果。原文未说明授权到期后如何处理此前生成的结果，也未给出识别质量目标。

检查：区分查看、运行、导出及角色范围；识别授权到期后的访问和产物生命周期缺口，不自行决定删除或永久保存；模拟页不能证明真实接入和识别能力。明确可开展任务/页面设计、需要数据与能力验证的范围和证据；不编造准确率或承诺完整识别能力。

## F：按阶段判断，不用覆盖率代替就绪

请求：评审一个 PRD 是否可进入设计和开发。全部需求有 ID 和来源；普通台账的对象、操作、权限与结果明确，字段类型及条件必填尚未细化；自动评分只有“按模型配置计算”，公式、输入样本未定。数据库与 API 设计在另一份文件，本轮未提供。不要修改 PRD，只给结论和最小补充项。

检查：台账可以进入详细功能设计，开发还需对应字段规格；自动评分需规则和样本，不能按覆盖率宣称可开发；未提供的技术规格标为未核验，不断言不存在；区分业务缺失、设计不足和后续规格。不把缺口变成全项目停工，也不自动修改文档。
