# 业务推演与就绪判断

用于复杂业务的设计与交付自查，或评审文档能否支持后续设计和开发。按任务涉及的风险选用，不要求简单查询填写全部表格，不默认追加 API、数据库或系统架构设计。

## 先确定判断对象

就绪结论应指向具体模块或业务链及下一项活动，例如原型设计、规则开发、能力验证或验收。不同活动需要的证据不同：

| 目标 | 需要明确的内容 | 不足时如何处理 |
|---|---|---|
| 业务评审与原型设计 | 范围、角色、对象、主要任务及结果；歧义有影响说明和可支持的候选 | 对受影响分支保留草案，继续已知部分 |
| 详细功能设计完成 | 相关业务字段、规则、状态动作、操作权限、页面和输出物；关键异常有结果 | 标明具体缺项，不以“按配置”或通用权限原则结项 |
| 对应模块开发 | 上述业务规格足以得到一致结果；外部依赖边界及必要技术契约可用；存在固定输入和明确预期 | 说明可实现的范围、尚待决定的逻辑或独立验证任务，关联已有技术规格而非抄入 PRD |
| 架构定型、采购或全量估算 | 适用规模、负载、留存恢复要求、复用/采购/自建边界及交付责任 | 不用模块数或原文列举的技术产品直接推算部署数和工作量 |

文档推演通过仅说明设计在所列条件下自洽；业务确认、实现完成、能力验证和系统验收分别记录。未提供技术材料应说明“本次未核验”，不能断言它不存在。

## 把规则展开到能判断结果

对决定路径、等级、清单、评分、计时或汇总的规则，定位适用对象、输入来源与单位、判定条件、优先级或组合关系、产出，以及适用时点/版本。只展开会影响结果的部分：

- 公式与阈值：区分 `>` 与 `≥`，明确窗口、分母、零值、缺失和异常值；未知阈值列为待确认，不能以 0 或任意默认值补齐。
- 路径与材料：不同条件对应哪些必需、可选或替代材料，缺项进入哪一步；一个通用附件上传入口不能证明各路径完整。
- 对象归属与匹配：明确匹配依据、零命中、多命中和时间版本。页面能选择某条记录，不等于自动归属有了判据；不擅自取第一条。
- 可配置规则：区分产品支持哪些配置、首批采用哪些规则、哪些尚待决定。配置值变化会改变路径或核心结果时，应作为关键决定。

能提出候选时，候选应把已有输入连接到可观察结果，并列出假设及其依据。无法支持候选时，只展开已知部分及缺失连接，不编造完整规则来凑验收用例。

## 用反例检查关键业务关系

优先选择会改变结果或权限的反例，避免只走一次成功流程。以下是检查方向，不是默认新增功能：

| 涉及关系 | 用于推演的反例 | 设计应回答的问题 |
|---|---|---|
| 多种状态 | 对象仍在使用，同时处于整改；任务暂停后继续 | 状态是否独立维度，合法组合及副作用是什么；只有需求包含恢复时才设计恢复去向 |
| 审批与生效 | 审批对象和无需审批对象共用页面 | 条件适用于哪个对象、动作与分支；不能将“审核后生效”推广至普通保存 |
| 权限与授权 | 可查询但不可导出；开始任务后授权到期 | 对应角色、对象/字段、操作、范围、状态和条件是否足以判定；已产生的数据或文件如何访问、保留和处置 |
| 多重匹配 | 同一目标属于多个对象；历史映射后来改变 | 是否能唯一归属、保留哪些候选或未知，以及结果使用哪个时点的依据 |
| 重复与迟到 | 相同输入再次到达；旧版本晚于新版本到达 | 哪一层、哪个对象识别重复，是否重复产生业务结果，旧输入是否能改写新结果 |
| 部分失败 | 本地成功、下游失败；输出生成中输入发生变化 | 哪方结果权威、用户看到什么、如何回查或补偿、使用哪版输入；具体消息与事务实现留给技术设计 |

对重复与失败的处理不能一律写“重试”：重试对象、已有成功结果及再次产生的副作用需明确。不同处理层的去重或归并不能共用一个含义不清的“去重规则”。

## 识别能力依赖与证据

涉及外部数据、设备、算法或模型时，将需求能力与必要输入、来源/供方、授权、样本、支持范围及已验证结果关联。区分真实接入、离线样本、模拟数据和仅有计划；任务管理页不证明实际处理能力。

确定性业务规则应能复算；模型输出可能存在波动，应明确输入输出、适用边界、评测样本、判断标准及必要的人工处理，不要求把模型内部强行写成业务公式。没有质量证据时保持能力待验证。

缺接口名称与缺数据可得性影响不同。前者可在已知业务契约上继续设计；后者应标出受影响能力，给出需验证的样本、字段或结果，不能把“预留接口”当成已满足。方案需引入替代处理时标为候选，不擅自降低原要求。

质量或性能要求保留原文数值及比较关系。是否能验收还取决于样本/负载、环境、观察方式和成功标准；未给出的准确率、吞吐、保留期或恢复目标不自行承诺。能力、规模与交付依赖只约束相关活动，不阻塞独立表单等无关工作。

## 推演输出必须能被复核

对关键规则选择正常案例和最能暴露歧义的边界，记录需求 ID、角色/前置状态、固定输入、规则或假设、动作、预期结果与依据。不能把“结果应正确”“确认配置后按规则执行”当作准确预期。

例如，原文明确“值大于阈值告警”，阈值未定：可以用**仅供推演的阈值 10**，检查 9、10、11 分别不触发、不触发、触发，并检查缺值规则是否明确。这验证了比较关系，不能据此将 10 写成正式默认值或声称该模块业务已确认。如果连比较关系也未知，先保留候选差异，不能编造唯一预期。

用例输出与规则、权限、状态或页面矛盾时，修订实际遗漏后再推演；不能只增加一条“待确认”掩盖本可修复的设计错误。真实业务缺失仅阻塞相关预期，不伪造已执行通过的结果。

## 交付时说明缺口归属与可先行范围

对每个关键缺口写清影响到的需求或业务链，区分：

- **材料或业务决定缺失**：需补充的事实/选择是什么，候选及影响是什么；已知责任角色和解决阶段可列出，未知时不指定人员或日期。
- **本轮设计遗漏或矛盾**：在约定深度内能够补写或修正的内容，应在交付前处理，保留真正未决部分。
- **下一阶段规格**：说明后续需要的字段细则、输出样张、技术契约或验证材料及用途，不反推本轮 PRD 必须包含全部实现设计。

复杂项目可用“模块/需求 ID—下一活动—结论及依据—阻塞问题—可先行范围—补齐后检查方式”简表。关键问题复用既有 ID，不另建重复清单。结论应明确哪部分可做、哪部分只可带假设设计或验证、哪部分尚不能定稿，并说明解除限制所需的决定或证据；这是一项设计判断，不新增审批制度。
