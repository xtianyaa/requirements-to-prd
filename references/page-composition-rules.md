# 页面组合与颗粒度规则

## 核心判断

页面不是功能清单的容器，而是用户完成一个相对完整任务的工作空间。

优先顺序：

用户任务 > 业务对象 > 数据上下文 > 角色/权限 > 生命周期 > 信息复杂度 > 功能清单颗粒度

## 合并判断

以下多数同时满足时优先合并：
- 同一用户目标；
- 同一核心业务对象；
- 同一数据上下文；
- 用户需要连续操作；
- 权限基本一致；
- 不造成明显信息过载。

典型：
- 列表查看 + 详情查看 + 处理动作：列表 + 详情；
- 多指标同一分析任务：一个分析页；
- 多层级分析：一个分析页内下钻；
- 多配置项：一个配置页。

## 拆分判断

出现以下任一强条件，可拆分：
- 用户目标完全不同；
- 核心对象不同；
- 角色/权限完全不同；
- 数据上下文完全不同；
- 生命周期阶段独立且操作方式明显不同；
- 需要独立导航入口；
- 合并后明显无法使用。

## 禁止机械拆分

不要因为存在：
- 一个指标；
- 一个按钮；
- 一个流程节点；
- 一个查询条件；
- 一个下钻层级；
- 一个弹窗/抽屉

就创建独立页面。

## 页面颗粒度复核

每个页面回答：
1. 为什么需要这个页面？
2. 用户在这里完成什么任务？
3. 承载哪些功能？
4. 如果把它与相邻页面合并，是否仍然清晰？
5. 如果删除它，是否有用户任务无法完成？

如果页面只承担很小的一部分任务，优先考虑合并。

## 典型组合策略

### 监测类
通常优先：
概览/工作台 → 分析 → 详情/预警详情

### 业务处理类
通常优先：
列表/工作台 → 详情/处置

### 配置类
通常优先：
配置列表 → 配置编辑

### 审批类
如果审批只是详情中的一个节点：
详情 + 审批操作区

如果审批任务具有独立待办、独立角色和独立工作方式：
审批工作台 + 详情

以上是设计启发，不是强制模板；必须结合原始需求判断。
