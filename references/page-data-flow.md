# 页面数据与操作规则

用于说明页面如何取得信息、用户如何发起动作、系统产生什么结果，以及后续如何读取或使用这些结果。描述业务层面的责任与变化，不默认设计数据库表和接口参数。

## 统一含义

| 项目 | 含义 |
|---|---|
| 进入上下文 | 查询条件、业务对象标识、上游选中项等；当前身份和权限范围作为访问约束 |
| 读取的数据 | 页面需要取得的业务记录、统计结果、状态和规则版本等 |
| 业务来源 | 数据由哪个已知系统、业务过程或操作产生；具体系统不明时保留未决 |
| 展示内容 | 呈现给用户的信息，不等同于对外输出或持久化变更 |
| 用户输入和动作 | 输入的内容、选择项及发起的操作 |
| 系统处理 | 权限、状态及业务校验；按规则计算、保存、派发或改变状态 |
| 处理结果 | 发生了哪些业务变化，成功或失败如何反馈 |
| 后续使用 | 当前页面刷新、其他页面重新读取、传递对象标识或筛选条件、进入后续流程 |

上游页面传递一个标识，不等于它产生了目标对象的全部数据。目标页面可能按标识从同一业务来源读取。显示统计结果也不代表统计由前端执行；实现责任未确定时写“系统按规则统计”。

来源不明确时区分：业务数据已知但具体源系统待确认，和数据本身是否存在尚不确定。不要仅因未知 API 名称就阻断功能设计，也不要把外部数据一定可得当成事实。

## 读数据任务

用一段说明或一张表回答：

1. 用户从哪里进入，携带什么查询或对象上下文？
2. 在什么权限范围内读取什么数据，哪些结果由系统计算，引用哪条业务规则？
3. 页面展示什么，空结果、缺少来源数据和读取失败如何区分？
4. 查看详情或下钻时，改变什么条件，打开哪个载体；返回时保留什么？

只读任务明确“无业务数据写入”。无需硬填保存、审批、下一节点等不适用内容。若原文要求查询或导出审计，单独描述系统留痕，不把它当成用户编辑。

示例仅说明表达方式，不是业务事实：查询条件与权限约束 → 系统读取汇总结果 → 列表展示 → 选择记录并传递标识 → 详情重新读取对象数据 → 返回原列表上下文。

## 写入或流转任务

关键操作可使用下表。简单查看不必强行套用完整写入模板。

| 动作 | 具体角色、当前状态及适用分支 | 用户输入 | 系统校验和规则引用 | 成功后的数据与状态 | 失败反馈及后续或待确认项 |
|---|---|---|---|---|---|

不能只写“提交后进入下一节点”。应指出提交了什么、发生了什么变化、由谁或什么事件继续；主路径未定时按主文件方法给出带假设的待评审走法，真实缺失定位到相应条件或分支。

页面操作条件引用主文件中的业务操作关系。若某类对象需要审批，其他类是否需要尚未明确，不得在共用页面将“已审批”写成所有后续操作的共同前提。角色名称、允许状态、输入约束及结果与业务流程保持一致，已知条件不能因其余细节未定而全部省略。

审批、必填、附件联合保存、互相依赖等会改变行为的条件，没有业务依据时只能作为明示的候选假设。不得一边将某条件列为待确认，一边按已确认规则强制禁用、拒绝保存或要求整组成功。候选可以比较“一次提交两份资料”和“分别保存后汇总提交”，说明数据及失败处理的差异，不因等待确认就关闭整个业务动作。

关注本任务确实涉及的异常，例如必填信息缺失、权限不足、状态已变化、保存失败；常见交互处理可作为设计建议，新增业务流转仍需依据。不要为普通页面附加一套无关的异常清单。

数据写入成功后，说明当前页面与相关列表如何反映最新结果。需要时区分暂存和提交；不在原文未要求时自动新增草稿、撤回、作废等业务能力。

## 自动处理

对无用户操作的节点，单独说明：触发事件或时间条件、所用数据、匹配或计算规则、产出、后续去向，以及影响业务结果的缺失或失败情况。

例如原文要求自动派发，只知道“责任部门可配置”时，可描述按配置匹配部门的设计建议，但仍需确认匹配优先级、多部门命中或无匹配如何处理。查看待办只覆盖展示，不能证明派发逻辑完整；不可擅自补成“派给管理员”。

自动产生的数据可被多个页面消费，不必制造前置页面作为数据来源。后台定时处理也不应被描述成进入某页后才触发。

## 跨页面与共用规则

每条关键页面关系说明：源载体、触发动作、目标载体、携带上下文、目标读取依据和返回方式。仅有关联时才写；不需要为所有页面构造串行链路。

先说明页面涉及的业务对象如何关联，再写跳转。至少说清影响操作的关联维度，例如对象、统计周期、明细范围及适用规则；已知一对一或一对多关系明确写出，未知且影响交互时提出具体问题。传一个标识不能代替解释其关联范围，无需因此预设数据库键或 API。

关联结果可能有多条时，说明用户在哪里选择：例如在当前页展开关联列表，或带筛选条件进入已有列表，再选中记录进入详情；只在已明确唯一目标时直接跳详情。零条结果如何表达、下钻后关联范围如何变化、返回如何恢复上下文，也需要和页面说明一致。

历史结果涉及规则变更、补数或重新计算时，区分结果产生时的依据和当前配置。材料未决定是保留原结果、替换结果还是生成新结果时，将结果关系和受影响跳转列为待确认，不把任一版本政策写成已确认事实。

规则定义独立维护，页面引用规则及其适用条件。业务流程说明对象生命周期；页面数据说明信息和变化；两者通过对象、动作与结果对应。对历史规则版本、跨角色处理等原文明确约束，在相关读取或操作中落实。

## 反查

展示信息能否找到业务来源？动作是否有足够输入和权限依据？自动节点是否有触发与产出？处理结果是否能被后续任务读取？失败是否被误当成功？页面拆分合并后是否丢失对象标识、筛选条件、返回关系或必要数据？

不能回答时指出断点及影响，按主文件规则标为部分描述或待确认；不以一条箭头连线表示问题已解决。
