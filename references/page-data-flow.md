# 页面数据流规则

## 目的

页面数据流用于说明“页面看到的数据从哪里来、经过什么处理、用户操作后到哪里去”。

它不是技术架构图，不要求数据库、API、消息队列等实现细节。

## 每个页面必填

1. 数据输入
2. 数据来源
3. 页面处理
4. 页面展示
5. 用户操作
6. 数据回写
7. 下游去向

如果原文没有明确来源，必须写“待确认”。

## 标准读流程

```text
数据来源
→ 查询/进入条件
→ 页面筛选/统计/组织
→ 页面展示
→ 用户查看/下钻
→ 下一页面
```

## 标准写流程

```text
用户输入/操作
→ 页面校验
→ 保存/提交
→ 数据或业务状态变化
→ 后续流程
→ 页面刷新/反馈
```

## 页面数据流和业务流程的区别

页面数据流：
- 关注数据；
- 关注页面输入、处理、展示、回写和输出。

业务流程：
- 关注业务事项；
- 关注角色、状态、节点和审批/处置顺序。

二者必须能够互相映射。

## 不允许擅自指定数据源

原文只写“医院业务数据”：
> 数据来源：医院业务数据，具体系统/接口待确认。

不要自行写：
> HIS / EMR / ERP / 数据仓库。

除非原文明确。

## 页面变更后的数据流检查

页面合并：
- 合并输入；
- 合并展示；
- 合并操作；
- 重新检查下游。

页面拆分：
- 明确哪个页面产生数据；
- 明确哪个页面消费数据；
- 明确页面间传递的数据；
- 检查业务流程是否断裂。
